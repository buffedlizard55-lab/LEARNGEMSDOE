The gate: no prediction file from this agent

This repository researches and documents. Submission generation — training a model that emits the single-band float32 GeoTIFF, validating it for score, and using one of the three-per-week slots — is a separate, explicitly gated process. Nothing here crosses that line:

  • No script writes a submission-shaped GeoTIFF.
  • No DrivenData API submitter, no credential handling, no upload path.
  • No copy of the reference notebook's training loop — only a link to it.
  • No weekly submission slot is consumed.

The distinction that matters: scoring a candidate map on a spatial holdout is research, and is what scripts/metrics.py is for. Producing the artefact that gets uploaded is submission generation, and is not done here.

One documented assumption in the metric

The problem description defines the kernel as k(d) = (1 − d/R)+ with R = 300 m, “i.e., 3 pixels at 100 m resolution”, but does not state whether d is measured between pixel centres or between pixel edges. scripts/metrics.py uses centre-to-centre Euclidean distance in metres, which is the only convention under which “3 pixels at 100 m” equals 300 m. This is an assumption, it is recorded in the module docstring, and it is the first thing to check if a local score ever disagrees with the public leaderboard.

What is missing before training could start

  1. Rasters in data/ — the blocker above.
  2. A training script. Not present, and not added by this agent. The reference solution's notebook is the official starting point; adapting it is a gated activity.
  3. An inference script that emits the submission GeoTIFF. Not present, by design.
  4. A spatial-holdout harness that wires metrics.py to block-specified folds. The metric exists; the harness does not.
  5. GPU for anything serious. The reference-solution README offers CUDA 12.6 / CUDA 13.0 environments; a CPU-only environment exists but the README states training is much faster on a GPU. Apple Silicon uses MPS.
